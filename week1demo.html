1. Week 1 作品说明

作品名称：ScoreLeaderboard — 基于任务认证的链上分数排行榜

一个部署在 Monad Testnet 上的智能合约，实现了任务系统 + 分数累加 + 实时排行榜的完整流程。

用户不直接输入分数，而是通过完成预定义任务（1/2/3/5/7/10 分六级）间接获得分数。合约自动累加并维护排行榜，任何人都可以链上查询排名。

// 核心流程
用户完成任务 → 验证者调用 completeTask(user, taskId) → 合约自动加分 → 排行榜实时更新
     │                                            │
     │  分值由合约定义，用户无法自行修改             │  任何人可查询，链上可验证
     └─────────────── 信任最小化 ──────────────────┘

项目文件：

  • 合约源码：leaderboard-contract/contracts/ScoreLeaderboard.sol
  • 编译脚本：leaderboard-contract/scripts/compile.js
  • 部署脚本：leaderboard-contract/scripts/deploy.js
  • 交互演示：leaderboard-contract/scripts/interact.js
  • 说明文档：leaderboard-contract/README.md

2.2 合约函数一览

类型函数说明
WritecompleteTask(user, taskId)验证者为用户标记任务完成，自动加分
WritebatchCompleteTasks(users[], taskIds[])批量完成，节省 Gas
WriteregisterTask(name, points)Owner 注册新任务类型
ReadgetScore(user)查用户总分
ReadgetRank(user)查用户排名
ReadgetLeaderboard()完整排行榜（已排序）
ReadgetTopN(n)Top N 排行榜
ReadgetUserSummary(user)分数+排名+任务数+是否注册

2.5 AI 辅助 vs 人工判断

任务AI 贡献人工贡献
合约设计建议 mapping + array 存储结构确定六级分值体系，设计权限模型
合约编写生成完整 Solidity 代码修复 NatSpec 编译错误（taskIds → taskIds_）
工程脚本编写 compile/deploy/interact选择 Remix 部署方式（安全考量）
任务分值建议 1/3/5/10 四级扩展为 1/2/3/5/7/10 六级
部署方式提供脚本方案改用 Remix + MetaMask（私钥不离开钱包）

5. Week 2 推进方向

计划推进的核心工作
  1. BattleEngine 核心合约：从伪代码推进到可部署的 Solidity 实现，包含 submitMove → 状态更新 → 胜负判定的完整对战循环。
  2. AgentNFT (ERC-721)：实现 Agent 铸造功能，每个 Agent 有独立属性，与排行榜系统集成。
  3. 前端对战画面：监听链上 MoveExecuted 事件，实时渲染排行榜更新。
需要助教或同伴帮助的问题
  1. Monad 并行执行：如果两个 completeTask 同时执行，是否需要特殊并发控制？如何设计合约最大化并行优势？
  2. Foundry vs Hardhat：多合约系统（5 个合约）应选哪个工具链？Monad Testnet 配置是否有坑？
  3. 链上事件 → 前端：400ms 出块频率下，直接监听 RPC event 够用吗？需要 The Graph 吗？
  4. 排行榜 Gas 优化：冒泡排序 O(n²) 在大规模用户时 Gas 很高，有没有更高效的链上排序方案？
